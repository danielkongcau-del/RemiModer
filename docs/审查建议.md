我先直接看你仓库里当前的事件队列、记录入队路径和高频桥接点实现，再给方案。这个问题本质上不是“把队列再加大”就能解决，而是要把**事件保真、采样语义和吞吐路径**分层，否则千万级事件会持续把系统拖垮。

我已经定位到两个不同的“溢出源”，而且你现在把它们都记成了同一个 `queue_overflow`：一类是**每个观察点的 `Cell` 池被回调打满**，另一类是 **Store 的 64 MiB seal backlog 达到上限**。在千万级事件下，单纯增大 `slots_per_point` 或 64 MiB 上限只会延后失败，不会解决吞吐失配。

我看了你现在 `main` 分支里的实现。这个问题已经不是“队列参数太小”，而是一个更根本的**信息率失配**：

> 高频桥接点的生产速率，长期高于“事件格式化 → 压缩 → 落盘”的持续吞吐率。

在“不阻塞游戏线程”的前提下，如果生产速率长期高于消费速率，那么**不存在一个有限队列可以实现无限时长、逐事件、零丢失采集**。能做的只有三件事：减少需要逐事件保存的信息、提高持续吞吐、或者阻塞生产者。第三个显然不适合你的游戏内观察器。

你的架构本来就强调 bounded channel + 独立 loss accounting，所以现在应该升级“证据保留策略”，而不是无限扩队列。

## 我先指出一个当前实现里的重要问题

你现在实际上有**两种完全不同的溢出，却都被记成 `queue_overflow`**。

第一种发生在观察点自己的 `Cell` pool：

```cpp
token.cell = p.Acquire();

if (!token.cell)
    p.loss.Note(...);   // 默认 QueueOverflow
```

每个 `Point` 有固定 `poolSize`，`Acquire()` 在没有空闲 `Cell` 时立即失败。

第二种其实已经到了 Storage：

```cpp
if (payload.size() >= 4 MiB && !EnqueueSeal())
    throw StoreBackpressure();
```

而 Store 的：

```cpp
MaxOutstandingSealBytes = 64 MiB
```

超过以后不等，而是 backpressure。

但 `WriteRecord()` 又把：

```cpp
catch (const StoreBackpressure&) {
    point.loss.Note(... LossReason::QueueOverflow);
}
```

记成同一个 `queue_overflow`。

所以**第一件事不是调参数，而是拆 LossReason**：

```text
record_pool_exhausted
store_backpressure
pair_frame_exhausted
thread_nesting_exhausted
storage_failure
```

否则现在看到“1000 万 queue overflow”，其实无法知道是：

```text
callback → Cell pool
```

先炸了，还是：

```text
Worker → Store → Sealer → Disk
```

先炸了。

# 更关键的是：你仓库里其实已经有解决高频桥接点的雏形

就是：

```text
first_per_entry_return_address
```

它现在的设计非常适合**高频桥接点**。

你的代码不是对重复事件直接丢弃，而是：

```text
每一次 callback
        ↓
读取 architectural return address
        ↓
按 return address 聚合
        ↓
count += 1
first_qpc / last_qpc 更新

第一次见到这个 key
        ↓
保存一条完整 ABI/read evidence

之后相同 key
        ↓
不再产生完整事件
```

所以：

```text
10,000,000 callbacks
```

如果实际上只有：

```text
37 个真实 callsite
```

最终不是保存 1000 万条 Record，而是：

```text
37 条完整原始样本
+
37 组：
    exact callback count
    first_qpc
    last_qpc
```

你的 `Point::Retain()` 已经这么实现了，并且整个 aggregate table 是预分配、无锁/无动态分配的。

README 也明确把它定义成：

> 每个 entry return address 统计所有 callback，只入队每个 key 的一个完整 ABI/read sample；duplicate suppression 是 deliberate policy，而不是 queue loss。

### 所以我建议立刻把“桥接点”和“语义点”分开

不要所有观察点都：

```text
retention = full
```

应该变成三层。

```text
A. 高频桥接点
   ↓
AGGREGATE

B. 中频执行器/调度点
   ↓
SELECTIVE FULL

C. 关键状态写入/生命周期点
   ↓
FULL
```

比如某个高频 Bridge 的问题只是：

> “到底有哪些 native callsite 会经过这里？”

那么没有任何理由保留：

```text
10000000 × 完整寄存器 + XMM + reads + JSON
```

只需要：

```text
callsite A → 7,238,190 hits
callsite B → 2,719,223 hits
callsite C →    42,587 hits
```

然后每个 caller 有一份完整样本。

**这不会降低 caller discovery 的证据质量。**

反而比“队列爆掉以后随机丢 40%”强得多。

# 但仅按 return address 聚合还不够

这是我认为下一步最值得扩展的功能。

现在的 key 是：

```text
key = [RSP]
```

即 caller return address。

对于某些桥接函数，同一个 callsite 可能处理：

```text
Object A
Object B
Object C
Task X
Task Y
Job Z
```

那么：

```text

```

粒度就过粗了。

我建议把 Retention 从：

```text
first_per_entry_return_address
```

推广成配置驱动的：

```text
aggregate_by
```

例如逻辑上：

```json
"retention": {
    "mode": "first_per_key",
    "key": [
        "entry_return_address",
        "rcx"
    ]
}
```

或者：

```text
key =
hash(
    return_address,
    receiver_raw_bits,
    validated_task_identity
)
```

注意这里仍然保持你原来的原则：

> key 是**原始可验证值**，并不自动宣称 `RCX == Entity*`。

数据库之后才做 semantic interpretation。

于是：

```text
10M callbacks
```

可以变成：

```text
caller A + object 1 → count
caller A + object 2 → count
caller A + object 3 → count
caller B + object 1 → count
...
```

仍然可以得到**完整的实际动态桥接关系计数**，却不需要保存一千万份完全重复的 ABI。

## 最终应该加一个真正的 Binary Fast Lane

我不会废掉现在的 evidence schema。

而是：

```text
Generation metadata
    ↓
一次写 schema/dictionary

event
    ↓
compact binary
```

例如 event 只记录：

```text

point_numeric_id
generation
qpc

register_bits

```

不要每一条都重复：

```text

   "rax": ...
```

这些字符串在同一 generation 下本来就是重复的。

```text

      ↓

      ├─ SQLite
      ├─ JSON
      └─ Perfetto
```

这样：

> **Raw BIN 才是真正 evidence-of-record，JSON 只是 projection。**

这其实比现在更符合你的总体架构。

# 你的 Store 也有一个明显吞吐热点

目前每 **4 MiB**：

```text
payload
 ↓
XPRESS_HUFF compress
 ↓
NewFile()
 ↓
FlushFileBuffers()
 ↓
MoveFileEx(... WRITE_THROUGH)
 ↓
Meta()
 ↓
FlushMeta()
 ↓
再次 FlushFileBuffers()
```

也就是一个很小的 chunk 上产生了相当强的 durability barrier。

而 `NewFile()` 本身确实对文件执行 `FlushFileBuffers()`。

对低速证据非常稳。

对持续数百 MB/s 的原始流会非常吃亏。

我建议改成：

```text
64 MiB evidence segment
    ├─ page 0  CRC
    ├─ page 1  CRC
    ├─ page 2  CRC
    ...
    └─ segment hash
           ↓
       1 × FlushFileBuffers
```

而不是：

```text
16 × 4 MiB
→ 16 次 chunk flush
→ 16 次 manifest flush
```

崩溃时允许最后一个：

```text
UNSEALED_TAIL
```

被判定为不完整即可。

之前已经 sealed 的页仍然有 CRC/hash。

这是**durability granularity 的调整**，不是降低证据完整性标准。

# Compression 也应该变成自适应的

你现在用：

```cpp
COMPRESS_ALGORITHM_XPRESS_HUFF
```

如果 CPU compression throughput < SSD raw write throughput，那么：

> 压缩反而是瓶颈。

而你的格式本来已经支持：

```text
compression_type = none
```

所以可以做：

```text
seal backlog < 16 MiB
    → XPRESS_HUFF

16–48 MiB
    → fast codec / less compression

> 48 MiB
    → none
```

核心原则：

> **宁可多写磁盘，也不要为了压缩把证据扔掉。**

当然要根据你的实际 `sealed_raw_payload_bytes / flush_ticks` 测量决定。
