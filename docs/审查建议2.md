## 1. 我发现了一个真正的 exact probe-pair 完整性漏洞

这是目前我最建议先修的。

你现在 exact promotion 的入口路径做得是对的。

进入 exact caller 后：

```cpp
AssignRetention(e, retained);
e.retentionSlotIndex = ...;
```

因此 `enter` Record 知道：

```text
retentionExact = true
retention key
caller return address
slot index
```

然后 exact caller 才进入 PairLedger、等待正常出口。

问题出现在 `finish()`。

当前 leave 构造大致是：

```cpp
auto& e = payload->cell->leave;

e.id = ...
e.invocation = ...
e.parent = ...
e.exitHookId = ...

Capture(...);
```

但是**没有把 `enter.retentionExact`、retention key 或 exact-lane 身份传播给 leave**。

偏偏你的持久化失败逻辑是：

```cpp
catch (const StoreBackpressure&) {
    if (point.retention == RetentionMode::Full || e.retentionExact)
        point.BreakExactCoverage(qpc);
}
```



于是出现一个非常具体的情况：

```text
Exact callback #100

ENTER
 └─ 成功写盘
    retentionExact=true

LEAVE
 └─ StoreBackpressure
    retentionExact=false   ← 当前实现
```

理论上这已经意味着：

```text
Exact stream 不完整
```

但当前 `WriteRecord()` **可能不会调用 `BreakExactCoverage()`**。

因此平台有机会继续报告：

```text
exact_stream_state = COMPLETE_SO_FAR
```

尽管这个 exact invocation 的出口已经丢了。

### 更隐蔽的一点

你现在：

```text
exact_promoted_records_persisted
```

本质上统计的也是带 `retentionSlotIndex` 的记录。

而这个 index 目前只赋给 enter。

所以现在：

```text
exact_promoted_callbacks = 100
exact_promoted_records_persisted = 100
```

只能证明：

> **100 个 exact callback 的入口代表记录持久化了。**

不能证明：

> 100 对 `enter + leave` 都持久化了。

但当前：

```cpp
classified_exact_records_complete_so_far =
    exactPersisted == exactCallbacks;
```

会给人一种“exact pair 完整”的错觉。

现有 `native_pair_gate.py` 只验证成功路径：

```text
10 enter
10 leave
1 aggregate sample
```

没有注入一个“**只让 exact leave 遭遇 StoreBackpressure**”的故障。

`native_exact_promotion.py` 又测试的是 entry-only promotion，因此同样覆盖不到这个问题。

### 建议修法

不要简单把一个 `persistedRecords` 变成“2 倍”。

最好正式拆成：

```text
exact_callbacks

exact_entries_persisted
exact_normal_exits_persisted

exact_pairs_persisted
```

leave 至少继承：

```text
retentionExact
retentionKeyHash
retentionEntryReturnAddress
retentionKeyPartCount
retentionKeyParts
```

然后一个 exact pair 的严格完成条件：

```text
entry persisted
AND
normal exit persisted
```

如果任意一边：

```text
record pool
store backpressure
storage failure
pair capacity
frame termination
```

失败，则：

```text
exact_coverage_end_qpc = first failure
exact_stream_state = BROKEN_WITH_GAPS
```

这个我会列为**正式实机采集前 P0**。

# 2. 跨 generation Hook overlap 还有一个小洞

你现在 Compile 阶段对于**同一个 generation** 的物理 probe 很严格：

- exact site 可以共享；
- partial overlap 拒绝。

这一点是正确的。

但是 `Runtime::Apply()` 中还有一个跨代边界问题。

`ensure()` 当前逻辑大致是：

```cpp
Hook* h = find_hook_with_same_target(address);

if (!h) {
    // 创建新 Hook
    // 此处才检查和所有 owned hooks 是否 overlap
}

if (!h->owned)
    Install(*h, site);
```



也就是说，partial-overlap 检查发生在：

```text
“这个地址以前从未出现过”
```

而不是：

```text
“本次准备安装这个物理 Hook”
```

因此理论上存在：

```text
Generation A
Hook A @ X
↓
后来 detach
但 Hook 对象还保留在 hooks[]

Generation B
Hook B @ X+8
当前 owned

Generation C
重新启用 Hook A @ X
```

这次：

```cpp
find_hook_with_same_target(X)
```

会找到旧的 A。

所以不会进入：

```cpp
if (!h) {
    overlap check
}
```

随后直接：

```cpp
Install(A)
```

于是有机会变成：

```text
A reserved span: X ... X+16
B reserved span: X+8 ... X+24
```

重叠。

这不是你当前一次性 41 点计划最容易触发的问题，但你已经支持：

- generation switch；
- campaign；
- clean stop 后重新 qualification；
- same-process reactivation。

所以长期一定应该封掉。

### 修复很简单

把规则变成：

```text
每一次 !h->owned → 准备 Install

都重新检查：

所有当前 owned PhysicalHook

完全同 site → share
不相交       → OK
部分相交     → reject
```

而不要把 overlap validation 只放在 Hook object 创建阶段。

然后增加一个 fixture：

```text
gen A: X
↓ detach A

gen B: X+8
↓ active

gen C: X
↓
必须在写任何目标字节之前 reject
```

我也会倾向在正式 campaign 前修。

# 3. 当前最大的“实机才可能暴露”的吞吐问题是 `mark`

你已经把原来的 Worker：

```text
scan every Point × every Cell
```

改成 tagged ready-index stack：

```text
callback
  ↓
QueueReady(cell)
  ↓
worker TakeReady()
```

这是明显的进步。

而 `Tick()` 现在确实只消费 ready batch。

但存在一个锁级别问题：

```cpp
Runtime::Tick()
{
    std::lock_guard lock(stateMutex);
    ...
    drain ready queue
}
```

而：

```cpp
Runtime::Mark()
{
    std::lock_guard lock(stateMutex);

    遍历所有 generations
    遍历所有 points
    RetentionSnapshot(...)
    PointMetricsSnapshot(...)
    Store::Status()

    构造大 Json

    FlushMetaDurable();  // 包含真实磁盘 Flush
}
```



尤其 `RetentionSnapshot()` 会遍历整个 aggregate table，并对所有已有 key 生成 JSON。

在这整个过程中：

> **Worker 无法获得 `stateMutex`。**

但 Gum callback **并没有停止**。

于是：

```text
游戏线程
 callback
 callback
 callback
 callback
     ↓
 Cell
 Cell
 Cell
 Cell
     ↓
 ready queue

         Worker
           ×
      被 Mark 的
      stateMutex 卡住
```

如果 Mark 只耗时 1 ms，没有问题。

如果：

```text
数万个 retention key
+
几十 observation
+
manifest fsync
```

让它耗掉几十甚至上百毫秒，那么你的：

```text
event_slots_per_observation
```

可能瞬间被填满。

最后出现：

```text
record_pool_exhausted
```

而这个 loss 不是游戏本身造成的，是**用户按了一次 mark 导致采集器自己暂停消费**。

更值得注意的是，`agent.cpp` 对 `mark`：

```cpp
runtime->Mark(...)

随后为了填 response["generation"]
又调用 runtime->Status()
```



而 `Status()` 又会：

- 重新生成 retention snapshot；
- 重新遍历 points；
- 甚至遍历 pool 统计 `queued_cells`。

所以一次 mark 实际是：

```text
昂贵 Mark
+
昂贵 Status
```

### 而你现在的实机协议恰好要求连续做 5 次 mark



这就不是理论问题了。

### 我建议改成

Mark 在锁内只做：

```text
mark_id++
mark_qpc
capture generation shared_ptr
capture lightweight atomic counters
```

然后立即释放 `stateMutex`。

完整 checkpoint：

```text
RetentionSnapshot
StoreStatus
JSON
fsync
```

让 Worker 或另外一个 metadata thread 处理。

或者更干净：

```text
Control thread
   ↓
CheckpointRequest

Worker
   ↓
在正常 drain 循环中
记录 snapshot boundary
   ↓
继续 drain records
   ↓
metadata thread durability
```

另外 `Mark()` 本身已经返回 generation/checkpoint 信息的话，就不要再为了 generation 调一次完整 `Status()`。

在还没改之前，我至少要求补一个：

### `mark_under_load`

fixture：

```text
高频 full/exact producer
持续运行
+
连续 20 次 mark

要求：
record_pool_exhausted == 0
store_backpressure == 0
ready_queue_high_water 有界
callback latency 无异常尖峰
```

目前我没有在仓库中看到这项压力测试。

# 4. Aggregate 首样本还有一个“可恢复性”问题

你的 aggregate 策略现在非常合理：

```text
每个 key 全量计数
+
第一份 full sample
```

而且临时 Cell pool 满时会把：

```cpp
sampleState
```

恢复成 missing，使后来的同 key callback 可以再次尝试。

很好。

但是如果：

```text
full sample
成功进入 Cell
↓
Worker WriteRecord
↓
StoreBackpressure
```

当前 `WriteRecord()` 只记：

```text
StoreBackpressure
```

不会把：

```text
slot.sampleState = 2
```

退回：

```text
0
```

。

于是以后这个 key：

```text
callback count++
```

照常继续，

但不会再尝试 representative sample。

最终：

```text
full_records_persisted = 0
complete_for_caller_counts = false
```

所以系统**不会误报完整**，这一点是好的。

但一次短暂 Store backlog 就会让这一 key 整轮采集永远无法恢复。

我会把它列为 **P1 reliability fix**：

```text
非 exact aggregate first-sample
遇 StoreBackpressure
    ↓
sampleState 2 → 0
    ↓
后续 callback 可以重试
```

同时 retained count 本身仍然连续、不回滚。

# 6. 离线 analyzer 还有一个小的覆盖区间漏洞

```python
covered = any(
    row.point == point
```

它并没有同时证明：

```text
coverage.begin_qpc
      <= mark_window.begin

and

coverage.end_qpc
      >= mark_window.end
```

在你现在正常的单 generation orchestration 下，大概率成立。

```text

module invalidation
malformed run folder

```

建议改成显式的 interval containment。

这是 fail-safe 增强，不是当前最紧急问题。

## 但这轮更新本身确实做对了很多东西

我不会否定 Codex 的整体工作。

和我上次看到的版本相比，现在已经明显修掉了几个架构级问题：

- 各种容量损失已经拆开，不再全部叫 `queue_overflow`；
- 增加 composite retention，而且真实 key parts 会比较，fingerprint 不被当作身份；
- exact caller promotion 已经变成确定性 gate；
- 非 exact 高频 caller 不创建 PairFrame；

- event dictionary 在 generation 发布前持久化，这个顺序是正确的；
- 32 MiB segment、256 MiB backlog、自适应关闭压缩已经实现；
- ready queue 替代全 pool 扫描；
- exact stream 一旦出现明确 loss 会永久标记 broken，而不会因为后面恢复继续宣称完整；
- `entry_analyze` 对一般 loss 处理相当保守，有 loss 会退到 `UNKNOWN`，而不是强行补结论。

所以现在已经不是“平台根本不能用”的阶段。
